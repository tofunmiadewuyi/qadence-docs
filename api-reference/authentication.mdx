All requests to the Check API must be authenticated using an API key passed as a Bearer token in the `Authorization` header. You can find and manage your API keys from the Check dashboard. Requests made without a valid key will be rejected with a `401 Unauthorized` response.

## Authorization Header

Include your API key in every request using the following header format:

```
Authorization: Bearer YOUR_API_KEY
```

Check API keys follow a predictable prefix convention:

- **`ck_live_`** — Production keys that operate on real data.
- **`ck_test_`** — Sandbox keys that use test data and never affect production.

The following examples show how to pass your API key across common HTTP clients:

<CodeGroup>

```bash curl
curl https://api.wearecheck.com/v1/checks \
  -H "Authorization: Bearer YOUR_API_KEY"
```

```python Python
import requests

response = requests.get(
    "https://api.wearecheck.com/v1/checks",
    headers={
        "Authorization": "Bearer YOUR_API_KEY"
    }
)

print(response.json())
```

```javascript Node.js
const response = await fetch("https://api.wearecheck.com/v1/checks", {
  headers: {
    Authorization: "Bearer YOUR_API_KEY",
  },
});

const data = await response.json();
console.log(data);
```

</CodeGroup>

## Test vs. Live Keys

Check provides two key environments so you can safely build and test without affecting production data.

| Key Type | Prefix | Environment |
|---|---|---|
| Test key | `ck_test_` | Sandbox — uses mock data, no real-world effects |
| Live key | `ck_live_` | Production — operates on real data |

<Note>
  Use test keys (`ck_test_`) during development and integration. Switch to a live key (`ck_live_`) only when you are ready to go live.
</Note>

Test and live keys are fully independent — a test key cannot access live resources, and vice versa.

## Error Responses

When authentication fails, the API returns a JSON error body alongside the relevant HTTP status code. The table below describes every authentication-related error code you may encounter:

| Code | HTTP Status | Description |
|---|---|---|
| `missing_api_key` | 401 | No `Authorization` header was provided in the request |
| `invalid_api_key` | 401 | The key does not exist, has been revoked, or is malformed |
| `insufficient_permissions` | 403 | The key is valid but lacks the required scope for this action |

All error responses follow the same structure. For example, an invalid key returns:

```json
{
  "error": {
    "code": "invalid_api_key",
    "message": "The API key provided is invalid or has been revoked.",
    "status": 401
  }
}
```

Use the `error.code` field in your application logic to distinguish between error types programmatically.

<Warning>
  Never expose live API keys (`ck_live_`) in client-side code, public repositories, or anywhere they could be read by untrusted parties. If a live key is ever compromised, revoke it immediately from the Check dashboard and issue a new one.
</Warning>
