When something goes wrong, the Check API returns a structured JSON error response alongside an appropriate HTTP status code. Every error payload follows the same shape, giving you both a human-readable message and a machine-readable `code` you can branch on in your code. This page documents the full set of status codes, error codes, and recommended handling patterns.

## Error Response Format

Error responses wrap the error details under a top-level `error` key:

```json
{
  "error": {
    "code": "invalid_api_key",
    "message": "The API key provided is invalid or has been revoked.",
    "status": 401
  }
}
```

| Field | Type | Description |
|---|---|---|
| `error.code` | string | Machine-readable identifier for the error type |
| `error.message` | string | Human-readable explanation of what went wrong |
| `error.status` | integer | The HTTP status code (mirrors the response status) |

<Tip>
Always branch your error-handling logic on `error.code` rather than `error.message`. Messages are intended for humans and may be updated over time; codes are stable and designed for programmatic use.
</Tip>

## HTTP Status Codes

| Status Code | Meaning | Common Cause |
|---|---|---|
| `200 OK` | Success | Request completed successfully |
| `201 Created` | Resource created | `POST` request succeeded and a new resource was created |
| `400 Bad Request` | Invalid input | Missing required field, malformed JSON, or invalid parameter value |
| `401 Unauthorized` | Authentication failed | Missing, expired, or invalid API key |
| `403 Forbidden` | Insufficient permissions | API key does not have the required scope for this action |
| `404 Not Found` | Resource missing | The ID does not exist or the resource has been deleted |
| `429 Too Many Requests` | Rate limited | Your integration has exceeded the allowed request rate |
| `500 Internal Server Error` | Server error | Unexpected failure on Check's side — retry with backoff |

## Error Codes

The following machine-readable codes may appear in the `error.code` field:

| Code | Status | Description |
|---|---|---|
| `invalid_api_key` | 401 | The API key is missing, malformed, or has been revoked |
| `insufficient_permissions` | 403 | The API key lacks the required scope for this operation |
| `validation_error` | 400 | One or more request fields failed validation |
| `resource_not_found` | 404 | The requested resource does not exist |
| `rate_limit_exceeded` | 429 | Too many requests in a short window — slow down and retry |
| `internal_error` | 500 | An unexpected error occurred on Check's servers |

<Warning>
If you receive an `internal_error`, wait a few seconds and retry the request using exponential backoff. If the error persists, contact [Check support](mailto:support@wearecheck.com) with the full response body and your request timestamp.
</Warning>

## Handling Errors

The pattern below shows how to inspect the HTTP status code and parse the structured error payload in cURL, Python, and Node.js.

<CodeGroup>
```bash cURL
# cURL outputs the HTTP status with -w; redirect body to a temp file for parsing
curl --silent \
  --output /tmp/response.json \
  --write-out "%{http_code}" \
  --request GET \
  --url https://api.wearecheck.com/v1/checks/chk_invalid \
  --header "Authorization: Bearer YOUR_API_KEY"

# Output: 404
# /tmp/response.json:
# {
#   "error": {
#     "code": "resource_not_found",
#     "message": "No check found with ID chk_invalid.",
#     "status": 404
#   }
# }
```

```python Python
import requests

response = requests.get(
    "https://api.wearecheck.com/v1/checks/chk_invalid",
    headers={"Authorization": "Bearer YOUR_API_KEY"},
)

if response.ok:
    check = response.json()["data"]
    print("Check:", check)
else:
    error = response.json().get("error", {})
    code = error.get("code")
    message = error.get("message")

    if code == "resource_not_found":
        print(f"Check not found: {message}")
    elif code == "invalid_api_key":
        print("Authentication failed — check your API key.")
    elif code == "rate_limit_exceeded":
        print("Rate limited — back off and retry.")
    else:
        print(f"Unexpected error [{code}]: {message}")
```

```javascript Node.js
const response = await fetch(
  "https://api.wearecheck.com/v1/checks/chk_invalid",
  {
    headers: { Authorization: "Bearer YOUR_API_KEY" },
  }
);

const body = await response.json();

if (response.ok) {
  console.log("Check:", body.data);
} else {
  const { code, message } = body.error;

  switch (code) {
    case "resource_not_found":
      console.error(`Check not found: ${message}`);
      break;
    case "invalid_api_key":
      console.error("Authentication failed — check your API key.");
      break;
    case "rate_limit_exceeded":
      console.error("Rate limited — back off and retry.");
      break;
    default:
      console.error(`Unexpected error [${code}]: ${message}`);
  }
}
```
</CodeGroup>

### Retry Guidance

<Accordion title="When should I retry a failed request?">
Not all errors are safe to retry:

- **`500 Internal Server Error`** — Safe to retry. Use exponential backoff (e.g., wait 1 s, then 2 s, then 4 s) and cap at 3–5 attempts.
- **`429 Too Many Requests`** — Safe to retry after the window resets. Check the `Retry-After` response header if present.
- **`400 Bad Request`** — Do **not** retry without fixing the request payload. The same malformed request will always return 400.
- **`401 Unauthorized`** — Do **not** retry without refreshing or replacing your API key.
- **`403 Forbidden`** — Do **not** retry. Your API key lacks the required scope; contact your account administrator.
- **`404 Not Found`** — Do **not** retry. Verify the resource ID is correct.
</Accordion>
