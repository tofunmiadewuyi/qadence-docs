Every interaction with the Check API follows a consistent contract: authenticated HTTPS requests with JSON bodies, and JSON responses wrapped in a predictable envelope. This page covers everything you need to know to construct valid requests and reliably parse responses — from required headers and supported HTTP methods through to how timestamps are formatted.

## Making Requests

All requests must be sent over HTTPS to the base URL:

```
https://api.wearecheck.com/v1
```

### Required Headers

Every request must include an `Authorization` header carrying your API key as a Bearer token:

```http
Authorization: Bearer YOUR_API_KEY
```

For requests that send a body — `POST` and `PATCH` — you must also include:

```http
Content-Type: application/json
```

Omitting `Content-Type` on a request with a body will result in a `400 Bad Request` response.

### Example: Creating a Check

<CodeGroup>
```bash cURL
curl --request POST \
  --url https://api.wearecheck.com/v1/checks \
  --header "Authorization: Bearer YOUR_API_KEY" \
  --header "Content-Type: application/json" \
  --data '{
    "name": "Identity Verification",
    "type": "identity_verification"
  }'
```

```python Python
import requests

response = requests.post(
    "https://api.wearecheck.com/v1/checks",
    headers={
        "Authorization": "Bearer YOUR_API_KEY",
        "Content-Type": "application/json",
    },
    json={
        "name": "Identity Verification",
        "type": "identity_verification",
    },
)

print(response.json())
```

```javascript Node.js
const response = await fetch("https://api.wearecheck.com/v1/checks", {
  method: "POST",
  headers: {
    "Authorization": "Bearer YOUR_API_KEY",
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    name: "Identity Verification",
    type: "identity_verification",
  }),
});

const data = await response.json();
console.log(data);
```
</CodeGroup>

<Note>
The Check API does not currently support idempotency keys for `POST` requests. If you receive a network timeout or ambiguous response, query `GET /checks` with a filter before retrying a create request to avoid duplicate resources.
</Note>

## Response Structure

All successful responses return a JSON body. The shape differs slightly between single-resource and list responses.

### Single-Resource Responses

A request targeting one resource (e.g., `GET /checks/{id}` or `POST /checks`) returns the resource nested under a top-level `data` key:

```json
{
  "data": {
    "id": "chk_01HXYZ123",
    "name": "Identity Verification",
    "status": "active",
    "created_at": "2024-01-15T10:30:00Z"
  }
}
```

Access the resource directly via `response["data"]` in your code.

### List Responses

Endpoints that return collections (e.g., `GET /checks`, `GET /results`) wrap the array under `data` and include a `meta` object with pagination details:

```json
{
  "data": [
    {
      "id": "chk_01HXYZ123",
      "name": "Identity Verification",
      "status": "active",
      "created_at": "2024-01-15T10:30:00Z"
    },
    {
      "id": "chk_01HXYZ456",
      "name": "Background Screening",
      "status": "active",
      "created_at": "2024-01-16T08:00:00Z"
    }
  ],
  "meta": {
    "page": 1,
    "per_page": 20,
    "total": 143,
    "total_pages": 8
  }
}
```

Use the `meta.total_pages` value to determine whether additional pages exist. See [Pagination](/concepts/pagination) for a full guide on iterating through large collections.

## HTTP Methods

The Check API uses standard HTTP verbs with consistent semantics across all endpoints:

| Method | Purpose | Example |
|---|---|---|
| `GET` | Retrieve a resource or list of resources | `GET /checks`, `GET /checks/{id}` |
| `POST` | Create a new resource | `POST /checks`, `POST /webhooks` |
| `PATCH` | Partially update an existing resource | `PATCH /checks/{id}` |
| `DELETE` | Remove a resource | `DELETE /webhooks/{id}` |

`GET` and `DELETE` requests must not include a request body. `POST` and `PATCH` requests must include a valid JSON body.

## Timestamps

All timestamps returned by the Check API are formatted as **ISO 8601 strings in UTC**:

```
2024-01-15T10:30:00Z
```

The trailing `Z` denotes UTC (zero offset). When constructing filters or recording events in your own systems, ensure you store and compare timestamps in UTC to avoid timezone-related inconsistencies. Libraries such as Python's `datetime.fromisoformat()` or JavaScript's `new Date()` parse this format natively.
